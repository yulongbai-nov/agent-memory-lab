# Candidate protocol v2: isolated contract

Status: an explicit, pure validation interface only. The production local writer, its v3 prompt, queues, cache keys, renderer, reader and existing candidate schema remain unchanged. This contract is not a deployed writer protocol. The next writer, data migration and review UI require separate implementation and acceptance.

The input is `{ "protocol": "candidate-v2", "candidates": [...] }`. Unknown or omitted protocol identifiers fail closed. There may be zero to four candidates. `decision`, `change`, `correction`, and `todo` retain the existing `claim` and exact `evidence` format; a `decision` also requires exactly one `basis`: `confirmed`, `proposed` or `uncertain`. Other kinds reject `basis`. Callers cannot provide `status`, `lifecycle` or extra properties. The application returns every accepted candidate with `status: "待核实"`; `basis` describes the subject's apparent business state and is never human approval. Replacing or cancelling an accepted decision remains an independently reviewed append-only lifecycle event.

The intended semantic criteria are: `confirmed` needs evidence that a choice was made; `proposed` needs evidence of an identifiable choice still awaiting a decision; `uncertain` marks a traceable decision topic whose decision status is not established. Casual conversation and a completed task alone need no candidate. These criteria are not implemented as pattern matching in the structural validator.

The validator checks exact fields, limits, supported version and enum values; each citation must match a supplied source/item/version and a nonempty contiguous quote from that source. It delegates these citation and duplicate checks to the unchanged v1 validator, then rejects a quote with unpaired UTF-16 surrogates. It does not verify raw-original byte spans; an integrating caller must verify source availability, exact original bytes and offsets separately. A candidate under the wrong scope is rejected when the caller supplies only records from the authorized scope; this API does not itself authenticate a caller or discover scope. It makes no writes and does not edit source data.

Structure is not semantic truth. A syntactically valid `confirmed` candidate whose evidence says only “under discussion” can pass this validator. Likewise, a completed task can be structurally encoded as `todo`; the validator does not perform NLP or decide when an empty list is semantically appropriate. Frozen, independently labeled synthetic examples in the tests distinguish intended semantic gold from what structural validation can establish. Those examples are an evaluation plan and do not claim a model passed them. A human review and later independent writer tests must determine whether the claim, type, basis and citations are substantively supported.

Older data continues through the existing validator unchanged: absence of `basis` is not backfilled or treated as `confirmed`. The v2 interface does not accept v1 inputs; the existing v1 interface does not accept v2 inputs. The v2 module has its own TypeScript declarations and runtime schema. Explicit routing, stdout parsing, schema compatibility, recovery and migration are future work rather than implicit conversion: the current writer's parser expects the existing envelope and has not been changed here.
