# Scoped ontology projection v0.1

This is a deterministic, rebuildable view of explicitly reviewed annotations and exact archived source revisions. It does not modify Tier 0 records, the archive schema, CouchDB, or SQLite. It does not infer facts, call a model, or synchronize a graph database.

`rebuildProjection({archive, scope, asOf, dependencies})` resolves every participating annotation target and correction evidence to an exact source revision in the same owner and project. The cited version must have nonblank semantic text and must not be marked truncated, incomplete, or a preview. It emits decision, change and task nodes; `SUPERSEDES` and `CORRECTS` edges require explicit `revises` IDs. A correction keeps the original target and, when present, its separate clarification evidence. A manual correction without new evidence remains explicitly without new evidence.

The `dependencies` input is a separate, explicitly approved sidecar array. Each entry is `{id, scope, taskId, decisionId, approved: true, evidence, quote?, effectiveAt?, knownAt?}` and connects a reviewed task to a reviewed decision root. The relation has its own exact scoped evidence, separate from the task and decision references. When a literal quote is supplied, the projection verifies it against the cited version’s archived normalized text. It does not retain the quote in projection output or claim raw-original proof. It does not claim that the archive annotation format itself supports dependency fields. Invalid, unapproved, dangling and cross-scope entries are rejected. Duplicate task–decision relationships and revision cycles are rejected. Explicit revision links remain structural; a `SUPERSEDES` edge is emitted only when both sides are confirmed, active, and effective at `asOf`. Conflicting confirmed heads are not resolved by arrival order.

`answerDependency({projection, decisionRootId})` follows confirmed active changes effective at the explicitly supplied RFC 3339 `asOf`, then returns the selected decision and its dependent open tasks with separate exact source references. Proposed or uncertain changes do not replace a confirmed decision. Missing effective times or multiple possible heads produce an ambiguous result. A correction has no recorded effective timestamp in the current annotation contract: if it applies to the selected head, the historical answer is ambiguous rather than inventing a time. Corrections to prior decisions remain visible in the projection even when a later confirmed change is selected. An explicit `current-known` mode applies one currently known correction while returning the original and effective evidence separately; a manual correction without new evidence has a null effective evidence reference. The mode does not establish when the correction became known.

A dependency has its own valid-time and knowledge-time boundaries; it never inherits the task time. An explicit `effectiveAt` may precede the relation evidence timestamp when the source describes a retrospective effective date. Without it, the evidence timestamp is a conservative earliest supported boundary, not proof of the actual effective time; if neither is available, the relationship timing is unknown. Each dependency edge labels this distinction with `effectiveAtBasis` (`explicit`, `evidence-time`, or `unknown`). `knownAt` is a separate sidecar-attested observation or approval boundary and cannot precede the timestamp of the cited evidence. In historical `as-of` mode, the knowledge cutoff defaults to `asOf`; an explicit `knowledgeCutoff` can be supplied independently in either mode. A relationship known after that cutoff is excluded, and a missing knowledge boundary is ambiguous when the relationship would otherwise be effective. With no knowledge cutoff, `current-known` can apply a later-known relationship retrospectively. These sidecar knowledge boundaries do not establish when decision or task reviews became known; their annotation contract does not record that observation time.

The synthetic test uses a DSH Tuesday decision, independent DSH clarification, Codex Wednesday change effective at noon, and an approved checklist dependency. At 12:30 it resolves Wednesday and the checklist with distinct references. The same fixture also exercises the existing current query and a simple local file baseline that reads the fixture records and filters by topic, effective time, and checklist text. This is a functional smoke comparison only; it is not a measured performance benchmark and makes no claim about production datasets.
